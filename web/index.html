一边是 Views

官方推荐的 Views 开发方式是 XML + Bindings：静态、难以动态变化，写起来远不如 Compose 痛快。而 Google 并不打算继续为 Views 添砖加瓦。

一边是 Compose

Jetpack Compose 确实强大，但它是一套全新的渲染体系。并非所有人都想离开 View——包括 Hibari 的作者。

于是有了 Hibari：核心目标是为 Views 引入 Compose 的特性，其实现大量参考了 Jetpack Compose。

三个核心概念

一切都由 Modifier 和 Attribute 构成，而 UI 的基本单元是 @Tunable 函数。

@Tunable 函数

等同 Compose 中的 @Composable：每个函数描述一部分 UI 的外观与行为，由编译器插件与运行时共同护航。

@Tunable
fun Greeting(name: String) {
    Text(text = "Hello, $name!")
}

Modifier 与 Attribute

Modifier 存储 Attribute 信息；View 类型、方向、尺寸……一切皆 Attribute。组件函数把它们拼到 Node 上。

fun Modifier.orientation(
    orientation: LinearOrientation
): Modifier {
    return this.thenViewAttribute<LinearLayout, LinearOrientation>(
        uniqueKey, orientation
    ) { /* setOrientation(...) */ }
}

uniqueKey

特殊的属性键：对它的引用会在编译期被替换为 UUID 字符串。运行时靠它在比对新旧节点树时定位同一个 Attribute。

// 编译前
thenViewAttribute(uniqueKey, value) { … }

// 编译后（示意）
thenViewAttribute("3f2a…c9", value) { … }

它如何工作

运行时维护一棵虚拟的节点树——Node。状态改变时，Hibari 发起一次 Retune（近似 Compose 的「重组」）。

  1. 描述@Tunable 函数被调用，产出带 Attribute 的 Node 树。
  2. 编译编译器插件替换 uniqueKey、检查 Tunable 调用规则。
  3. 变更所依赖的状态改变，触发一次 Retune，生成新的节点树。
  4. 比对按 Attribute key 对比新旧两棵树，找出真正的差异。
  5. 应用只把变化下发给真实的 View，而不是重建一切。

    模块地图

    仓库按职责拆分，从注解、编译器插件到运行时、组件库与 Wear OS 层。

    语言与编译

    hibari-runtime-annotations
    @Tunable、@DisallowTunableCalls 等注解
    hibari-compiler
    Kotlin（K2）编译器插件：调用检查与 uniqueKey 替换
    hibari-runtime-lint
    Lint 规则：Tunable 命名与用法检查

    运行时与基础

    hibari-runtime
    虚拟节点树、Attribute 比对与 Retune
    hibari-ui
    Modifier、节点模型与基础 UI 类型
    hibari-ui-graphics
    Path、角度等图形原语
    hibari-foundation
    布局、边距、动态尺寸等基础 Attribute

    组件与扩展

    hibari-material
    Material Components 封装（推荐的组件库）
    hibari-animation
    Animatable、进出场过渡与缓动
    hibari-recyclerview
    HibariAdapter / ViewHolder 与分页作用域
    hibari-wear
    Wear OS 组件层
    app · wear-sample
    手机与手表示例应用
